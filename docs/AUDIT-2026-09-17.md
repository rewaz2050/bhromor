## 2. Order flow — shorten to 4 customer-visible steps: **YES, recommended**

### 2a. What exists today (8 statuses, 6 admin clicks + rider clicks)

```
DB enum ps_order_status (bootstrap L49):
  pending → confirmed → preparing → ready-for-pickup → courier-assigned → out-for-delivery → delivered
                                                                                          ↘ cancelled (from pending/confirmed/preparing only)
Who clicks what:
  admin/vendor : pending→confirmed  confirmed→preparing  preparing→ready-for-pickup      (3 clicks)
  DB trigger   : ready-for-pickup  → offers to nearest online rider (trg_orders_auto_dispatch)
  rider        : accept → courier-assigned ; pickup → out-for-delivery ; deliver(4-digit code) → delivered
```

`ps_advance_order` (bootstrap L5780) enforces **strictly +1 position** on `ps_order_flow`, so admin literally cannot skip "preparing" today — every order costs 3 separate taps before a rider can even be offered it. For a 45-minute-delivery shop that is the real problem, not the names.

### 2b. Proposal — 4 steps outside, same 8 states inside

Keep the DB enum exactly as is (44 references to `'delivered'`, 19 to `'ready-for-pickup'` in triggers/RPCs, ledger, dispatch, return flow — renaming the enum is a week of risk for zero customer value). Change **what people see and how many times they tap**:

| Customer / admin sees | Internal states it covers | Who moves it |
|---|---|---|
| **1. Order placed** | `pending` | customer (checkout) |
| **2. Confirmed** | `confirmed`, `preparing` | admin **one tap** "Confirm" → DB goes `pending→confirmed` |
| **3. Picked up** (rider has it) | `ready-for-pickup`, `courier-assigned`, `out-for-delivery` | admin **one tap** "Ready — call rider" → DB `→ready-for-pickup` → auto-dispatch → rider accepts → rider taps Pickup |
| **4. Delivered** | `delivered` | rider (4-digit code) |
| — Cancelled | `cancelled` | admin (while in step 1–2) |

Admin goes from **3 taps to 2 taps** per order; the customer's track page shows 4 clean steps instead of 6; nothing in the database, ledger, dispatch, payment-verify or returns changes.

> Owner's suggested order was "Order, Picked, Confirmed, In transit". Confirmed must come before Picked (the shop confirms stock/payment first, then the rider picks up) — so the honest sequence is **Order → Confirmed → Picked up → Delivered**. "In transit" and "Picked up" are the same moment for a 45-minute hyperlocal delivery (the rider picks up and is immediately on the way), so I fold them into one step with a live "rider on the way" sub-line + the map that already exists.

### 2c. Exactly what changes (one batch, ~8 files + 1 small migration)

## 3. Loading time — where the seconds go and what to cut

### 3a. Measured (production build, this sandbox)

| Page | HTML | JS on first load (raw / gzip) | CSS | Fonts |
|---|---|---|---|---|
| `/` | 45 KB | 15 files, **1039 KB raw ≈ 300 KB gz** | 127 KB (20 gz) | subsetted `unicode-range`, `font-display: swap` ✅ |
| `/shop` | 69 KB | 1033 KB raw | same | |
| `/checkout` | 42 KB | 1090 KB raw | same | |
| `/admin` | 8 KB | 930 KB raw | same | |

Biggest client chunks: **253 KB `@supabase/*` (auth-js, ssr, supabase-js, realtime, storage) — loaded on the storefront homepage** where nothing uses it (storefront auth is phone+password via `/api/account/*`; only admin/rider/vendor need the browser client), 223 KB react-dom (unavoidable), 151 + 109 KB Next runtime, 33 KB `lenis` smooth-scroll on every page.

### 3b. The real cost is round trips, not bytes

Dhaka → Vercel (default region **iad1, US-East**) → Supabase (region unknown — check) → back. Each hop ≈ 200–250 ms from Dhaka. Every page today does this:

**Storefront first paint (`/`)**
1. HTML (dynamic — `force-dynamic` on 101 routes, so no CDN cache; `getSupabaseServer()` reads cookies on every render)
2. JS ≈ 300 KB gz
3. Then **5 parallel client fetches before content appears**: `/api/products` (7 DB queries: products, variants, media, categories, zones, shops, sales view — the whole catalog every time, `no-store`), `/api/homepage`, `/api/promo`, `/api/account/me`, `/api/live`
4. Product grid paints only after (3) → **blank skeleton for ≈ 1.5–3 s on a Dhaka 4G phone**, even though the same catalog was rendered server-side one second earlier for `/shop`.

**Admin dashboard**
- `/api/admin/me` probe + `/api/admin/orders` (+ notifications, catalog, settings) — each admin API call re-does `requireStaff()` = **2 Supabase round trips (auth `getUser` + `admin_users` lookup) before the real query**; orders list poll every 10 s, notifications every 15 s.

**Rider job list (`/api/rider/jobs`)** — `listRiderJobs` calls `toDomain()` **per job**, and `toDomain` is 4–6 sequential/parallel queries (items, history, zone, coupon, products, media, return child, parent, assignment, rider) → **10 jobs ≈ 60 queries** on every refresh. Same pattern in `listDispatchJobs` (admin dispatch board), `listAwaitingDispatchOrders`, vendor orders (`limit 100` → up to 600 queries). This is the single biggest server-side latency source for admin/rider.

**Checkout** — `loadOrderSnapshot()` runs **10 queries** on every `POST /api/orders` (full catalog + coupons + shops + zones + ops settings + referral tables + up to 5 000 phone rows) just to validate one order; then `ps_place_order` (8 triggers) and a **second full `toDomain` read** to echo the order back.

### 3c. Fix plan — 3 batches, biggest win first

**P1 — Server: cache the catalog, batch the reads (≈ 60–70 % of perceived time)**
| # | Change | Effect |
|---|---|---|
| P1.1 | `/api/products`, `/api/zones`, `/api/homepage`, `/api/promo`, `/api/shops`: replace `no-store` with `Cache-Control: public, s-maxage=60, stale-while-revalidate=300` (Vercel edge cache) + `revalidateTag` on admin product/zone/settings writes | catalog served from Vercel edge in ~50 ms instead of ~600–900 ms; DB reads drop ~95 % |
| P1.2 | `fetchLiveCatalog()` wrapped in `unstable_cache`/`"use cache"` with tags (`catalog`, `zones`) so SSR pages (`/shop`, `/product/[slug]`, `/shops`) stop re-querying 7 tables per view | |
| P1.3 | **Batch `toDomain`**: new `toDomainMany(rows)` that fetches items/history/zones/coupons/products/media/assignments/riders with `.in()` once (the pattern `listOrders` already uses) and use it in `listRiderJobs`, `listDispatchJobs`, `listAwaitingDispatchOrders`, vendor orders | rider job list 60 queries → 8; dispatch board same |
| P1.4 | `loadOrderSnapshot()` trimmed: only the products in the cart (`.in(id)`), coupon by code, zone by id; drop the 5 000-phone scan behind a `count` query | checkout POST 10 queries → 4–5 |
| P1.5 | DB indexes missing for hot paths: `orders (status, created_at desc)` (admin list filters), `delivery_assignments (rider_id, state)` (rider jobs), `orders (rider_id) where rider_id is not null` | small, safe migration |

**P2 — Client: paint with server data, drop dead weight (≈ 20–30 %)**
| # | Change | Effect |
|---|---|---|
| P2.1 | Homepage / shop: pass the SSR catalog into the live registry (`hydrateLiveCatalog(initial)`) so the first paint shows products **without waiting for `/api/products`**; the client fetch becomes a background refresh | removes the 1.5–3 s skeleton on every storefront visit |
| P2.2 | Lazy-load `@supabase/*` — it is only imported by `admin-api.ts`, `admin-auth.ts`, `use-rider.ts`, `use-vendor.ts`, `rider/login`; make `getSupabaseBrowser()` a dynamic `import()` so the 253 KB chunk never ships to the storefront | −66 KB gz on every public page |
| P2.3 | `lenis` smooth scroll: dynamic import after first paint, and skip on touch devices (it multiplies touch scroll 1.8× and costs a rAF loop — phones do not benefit) | −8 KB gz + smoother scrolling on Android |
| P2.4 | `Reveal` sets `opacity:0` in an effect → content flashes in late on slow JS; switch to CSS `@starting-style`/`animation-timeline` or only animate below the fold | faster visible LCP |
| P2.5 | `/api/account/me`, `/api/live`, `/api/promo` on the homepage: defer until idle (`requestIdleCallback`) — none of them gate content | fewer competing requests at start |
| P2.6 | Admin: add `Authorization: Bearer` from the cached session to `apiGet` (it already exists for `apiSend`) so `requireStaff()` can skip the cookie refresh path; cache the `admin_users` role lookup for 60 s per user id in-process | each admin API call −1 DB round trip |

**P3 — Infrastructure (owner does, 10 minutes, largest single win for Dhaka users)**
| # | Change | Effect |
|---|---|---|
| P3.1 | **Vercel → Settings → Functions → Region: `sin1` (Singapore)** or `bom1` (Mumbai) — must match where the Supabase project lives (Supabase dashboard → Settings → General → Region). Today the default is `iad1` (Washington DC): every API call is Dhaka→US→(Supabase)→US→Dhaka | −300 to −600 ms **per request**; the cheapest, biggest fix |
| P3.2 | If the Supabase project is in US-East too, the fix is P3.1 + keep them together; moving a Supabase project = new project + `pg_dump`/restore (doable now while data is small; I can write the runbook) | |
| P3.3 | Cloudinary URLs: make sure product images are served with `f_auto,q_auto,w_<size>` transforms (uploader should store the base URL; `next/image` already resizes, but Cloudinary originals are often 2–5 MB) | image bytes ÷ 5–10 |
